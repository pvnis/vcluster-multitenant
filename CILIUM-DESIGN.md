# Integrating Cilium with gVisor and vCluster

Design for network isolation on the multi-tenant bare-metal cluster: east-west
between tenants, and north-south to the outside world.

Status: **applied and verified**, 10 August 2026. Cilium 1.19.5, kube-proxy
replaced, all 10 isolation tests passing, GPU stack unaffected. See
[Results](#results).

---

## The three facts this design is built on

Everything below follows from three things that were verified rather than
assumed.

### 1. vCluster has no CNI, so this is a host-cluster decision

Tenant pods are ordinary host pods in the tenant's host namespace, scheduled by
the host kubelet, wired by the host CNI. Nothing tenant-side participates in
networking. "What CNI for vCluster" is really "what CNI for the host", answered
with tenant isolation in mind.

### 2. Cilium deny rules override every allow — including a tenant's

This is the property the whole design rests on, and it is the one thing plain
NetworkPolicy cannot do. From the Cilium documentation:

> Deny policies take precedence over allow policies, regardless of whether they
> are a Cilium Network Policy, a Clusterwide Cilium Network Policy or even a
> Kubernetes Network Policy.

Kubernetes NetworkPolicy is *additive-allow*: if any policy permits a flow, it
is permitted. That means under plain NetworkPolicy, any policy a tenant is
allowed to author can only ever *widen* what that tenant can reach. There is no
way to write a floor a tenant cannot raise.

Cilium's `ingressDeny` / `egressDeny` give us that floor.

### 3. gVisor breaks Cilium's socket-level load balancing — and Cilium knows it

Cilium's default kube-proxy replacement does service translation in a cgroup-
attached eBPF hook on `connect()` / `sendmsg()`. A gVisor pod never issues those
syscalls on the host: the Sentry implements TCP itself in userspace and emits
finished packets onto the veth. The cgroup hook never fires, so ClusterIP
resolution silently fails for every sandboxed pod.

Cilium documents the fix and names gVisor explicitly alongside Kata Containers
and KubeVirt:

```
socketLB.hostNamespaceOnly=true
```

This bypasses the socket rewrite and falls back to the tc load-balancer at the
veth — which *does* see gVisor's packets, because those are real packets on a
real device. **This single setting is the entire gVisor/Cilium integration.**
Everything else about Cilium is indifferent to the sandbox, because gVisor's
netstack emits ordinary frames that hit `bpf_lxc` on the host side of the veth
exactly like any runc pod's would.

## Architecture

```
                        ┌─────────────────────────────────────────┐
   north-south          │  Layer 1  CiliumClusterwideNetworkPolicy │  cluster-scoped
   ─────────────▶       │           ingressDeny / egressDeny       │  tenants cannot
                        │           THE FLOOR — deny always wins   │  see or edit
                        └─────────────────────────────────────────┘
                                          ▲ overrides
                        ┌─────────────────────────────────────────┐
                        │  Layer 2  CiliumNetworkPolicy            │  host namespace
                        │           per-tenant allow-list          │  platform-managed
                        └─────────────────────────────────────────┘
                                          ▲ union
                        ┌─────────────────────────────────────────┐
                        │  Layer 3  tenant NetworkPolicy (synced)  │  tenant-authored
                        │           self-microsegmentation only    │  can only widen
                        └─────────────────────────────────────────┘
```

The layering is the point. Layer 3 exists so tenants get real self-service
segmentation, and Layer 1 exists so that self-service can never become an
escape. A tenant who writes `allow egress to 0.0.0.0/0` widens Layer 2 and is
still stopped dead by Layer 1.

### Layer 1 — the inviolable floor

Cluster-scoped, so it lives in no namespace, so vCluster cannot sync it into a
tenant and a tenant cannot see, edit, or delete it. One per tenant, generated by
the platform:

```yaml
apiVersion: cilium.io/v2
kind: CiliumClusterwideNetworkPolicy
metadata:
  name: tenant-a-floor
spec:
  endpointSelector:
    matchLabels:
      io.cilium.k8s.namespace.labels.tenant: tenant-a
  ingressDeny:
    # Any endpoint belonging to a *different* tenant.
    - fromEndpoints:
        - matchExpressions:
            - {key: io.cilium.k8s.namespace.labels.tenant, operator: Exists}
            - {key: io.cilium.k8s.namespace.labels.tenant, operator: NotIn, values: [tenant-a]}
  egressDeny:
    - toEndpoints:
        - matchExpressions:
            - {key: io.cilium.k8s.namespace.labels.tenant, operator: Exists}
            - {key: io.cilium.k8s.namespace.labels.tenant, operator: NotIn, values: [tenant-a]}
    # North-south: everything off-cluster, with cluster-internal carved out.
    - toCIDRSet:
        - cidr: 0.0.0.0/0
          except:
            - 10.42.0.0/16   # pod CIDR
            - 10.43.0.0/16   # service CIDR (includes kube-dns 10.43.0.10)
```

Tenant namespaces get labelled `tenant: <name>`, and Cilium exposes namespace
labels to selectors as `io.cilium.k8s.namespace.labels.<key>`.

Granting a tenant internet access is then an explicit platform act: add the
destination to the `except` list. Note this is deliberately an *exception to a
deny*, not an allow rule — because an allow could be duplicated by the tenant,
and an exception to a deny cannot.

### Layer 2 — per-tenant allow-list

A `CiliumNetworkPolicy` in the tenant's host namespace. Its job is to select the
tenant's endpoints for egress, which is what puts them into egress default-deny
in the first place, and then enumerate what they legitimately need: DNS, their
own vCluster API, same-tenant pods.

### Layer 3 — tenant self-service

Turn on the sync that is currently off:

```yaml
sync:
  toHost:
    networkPolicies:
      enabled: true
```

This closes a verified silent-failure trap. Today a tenant can author a
NetworkPolicy, see it in their own cluster, and have it do **absolutely
nothing** — it never reaches the host:

```console
$ KUBECONFIG=kubeconfigs/tenant-a.yaml kubectl get netpol
NAME              POD-SELECTOR   AGE
tenant-authored   <none>         6s

$ kubectl -n tenant-a get netpol          # the host
allow-same-tenant      <none>   79m
default-deny-ingress   <none>   79m       # tenant's policy is simply absent
```

A tenant believing they have segmented their application when they have not is
worse than a tenant knowing they cannot. Enabling the sync is only safe
*because* Layer 1 exists.

## The control-plane carve-out

The one genuine subtlety. A tenant's host namespace contains two very different
kinds of pod:

| | selector | needs host API? |
|---|---|---|
| vCluster control plane | `app=vcluster` | **yes** — the syncer creates host pods |
| tenant workloads | `vcluster.loft.sh/managed-by: <tenant>` | no |

Layer 1 must select **workload pods only**. A blanket namespace-wide deny of the
service CIDR would cut the syncer off from `10.43.0.1` and break the tenant's
cluster entirely.

**Settled by testing on 10 Aug 2026 — and the first design was wrong.** See
[Label forgery](#label-forgery-what-a-tenant-can-and-cannot-fake). Layer 1
originally carved the control plane out with `app NotIn [vcluster]`. That is
forgeable and has been replaced by an exclusion on the service account, which is
not.

## Why kube-proxy replacement, given it costs us the socketLB workaround

Tempting to keep kube-proxy and avoid the gVisor interaction entirely. The
reason not to is egress policy correctness, which is precisely what was asked
for here.

Without KPR, kube-proxy DNATs ClusterIP → backend in host iptables, *after* the
packet has already passed Cilium's `from-container` hook. Cilium therefore
evaluates egress policy against a service VIP that carries no workload identity,
rather than against the real backend. With KPR, `bpf_lxc` does the translation
itself and egress policy sees true identities.

So: KPR on, and pay for it with one documented, Cilium-supported setting.

## Migration plan

Pod CIDR `10.42.0.0/16`, service CIDR `10.43.0.0/16`, node `192.168.0.198`,
k3s `v1.36.2+k3s1`, kernel `6.8.0-117-generic` (ample for eBPF; cgroup2 and
the bpf fs are already mounted).

### Step 1 — k3s flags

```
--flannel-backend=none
--disable-network-policy
--disable-kube-proxy
--egress-selector-mode=cluster
```

`--egress-selector-mode=cluster` is **not optional** here. The default `agent`
mode requires kube-proxy for service-endpoint access, so removing kube-proxy
without changing it breaks `kubectl logs` and `kubectl exec` — which is exactly
the tenant-facing kubelet path the existing `:10250` NetworkPolicy rule exists
to protect. `pod` mode is unsuitable because Cilium's cluster-pool IPAM does not
allocate from `node.spec.podCIDR`.

### Step 2 — Cilium

```bash
cilium install --version 1.19.5 \
  --set ipam.operator.clusterPoolIPv4PodCIDRList=10.42.0.0/16 \
  --set kubeProxyReplacement=true \
  --set k8sServiceHost=192.168.0.198 \
  --set k8sServicePort=6443 \
  --set socketLB.hostNamespaceOnly=true \
  --set bpf.masquerade=true \
  --set hubble.enabled=true \
  --set hubble.relay.enabled=true
```

`k8sServiceHost`/`k8sServicePort` are required under KPR: with no kube-proxy,
the agent cannot reach the API server through the `kubernetes` service it is
itself responsible for programming.

Then remove the stale flannel state so it cannot conflict: the leftover
`10-flannel.conflist`, plus the `cni0` and `flannel.1` interfaces.

### Step 3 — tenants

Add `sync.toHost.networkPolicies.enabled: true` to `values/tenant.yaml`, upgrade
both vClusters, label both namespaces `tenant=<name>`, apply Layers 1 and 2.

### Rollback

Cluster state is backed up in `backup-20260810-100812/` (all namespaces, pods,
services, netpols, quotas, runtime classes, the flannel conflist, the k3s unit
as it was, and the helm release list). Rollback is: drop the four k3s flags,
restore the flannel conflist, restart k3s, `cilium uninstall`.

## Test plan

The existing NetworkPolicy tests taught a lesson worth repeating here: **one-shot
probe pods lie.** A pod whose `wget` fires at container start hits a ~2s window
during which the policy controller has not yet programmed the new pod's identity,
and returns a connection error that looks exactly like successful enforcement.
Two false "cross-tenant blocked" conclusions came from this. Every probe below
must therefore be a **retry loop over ≥60s**, and must be run in both directions.

Cilium should shrink that race — identity is label-derived rather than
IP/ipset-derived — and confirming it does is itself a test worth running.

1. **Baseline** — Cilium healthy, all pods running, DNS resolves, `cilium status`
   reports KPR enabled and socketLB in host-namespace-only mode.
2. **gVisor service resolution** — a `runtimeClassName: gvisor` pod resolves and
   reaches a ClusterIP. This is the socketLB fix; if it fails, everything else is
   moot. Compare against a runc pod to isolate sandbox-specific failure.
3. **East-west, tenant→tenant** — blocked, both directions, 60s retry.
4. **East-west, intra-tenant** — reachable, and measure how quickly after pod
   start (the kube-router figure to beat is ~2s).
5. **Tenant cannot raise the floor** — tenant authors an allow-all NetworkPolicy
   in their own cluster; verify it now *reaches* the host (Layer 3 works) *and*
   that cross-tenant traffic is still blocked (Layer 1 wins). This is the single
   most important test in the list; it is the whole thesis of the design.
6. **North-south egress** — tenant pod cannot reach the internet; verify it also
   cannot after the tenant writes an allow-all egress policy.
7. **Host protection** — tenant workload cannot reach `10.43.0.1` or the node IP;
   vCluster syncer still can (else the tenant cluster dies).
8. **Tenant API still reachable** — NodePorts 30443 / 31443 still serve both
   tenant kubeconfigs; `kubectl logs` and `kubectl exec` work through the
   vCluster kubelet proxy (this is what validates `--egress-selector-mode`).
9. **GPU stack unbroken** — re-run the two-tenant GPU share: HAMi scheduling,
   nvproxy memory limit refusal at 320 MiB against a 512 MiB cap, and the
   two-tenant compute split. Networking should be orthogonal to nvproxy, and
   confirming that is cheap.

**Note before running #9:** the installed `runsc` is
`release-20260727.0-84-g4ae651456bfb-dirty`, which is the pre-multi-GPU commit,
*not* the current branch head (`0583e626e`). Rebuild and reinstall first, or the
GPU results will not correspond to the code in the tree. Also keep
`--measure-usage=false` on the scheduler, per the known pmon defect.

## Results

Run 10 August 2026 with `test-isolation.sh`, against probe pods that are
long-lived and driven by `kubectl exec`, so every result is a retry over time
rather than a single connection at pod start.

```
1. gVisor + Cilium: service resolution through a ClusterIP
  PASS tenant-a: ClusterIP by DNS name (reachable after 1s)
  PASS tenant-b: ClusterIP by DNS name (reachable after 0s)
2. Intra-tenant pod-to-pod
  PASS tenant-a client -> own server by pod IP (reachable after 0s)
  PASS tenant-b client -> own server by pod IP (reachable after 0s)
3. Cross-tenant (east-west) -- must be blocked, both directions
  PASS tenant-a client -> tenant-b server (blocked for 60s, 12 attempts)
  PASS tenant-b client -> tenant-a server (blocked for 60s, 12 attempts)
4. North-south egress -- must be blocked
  PASS tenant-a -> internet by IP (blocked for 60s, 12 attempts)
  PASS tenant-b -> internet by IP (blocked for 60s, 12 attempts)
5. Host control plane -- must be blocked
  PASS tenant-a workload -> host API server (blocked for 60s, 23 attempts)
  PASS tenant-b workload -> host API server (blocked for 60s, 23 attempts)

passed 10, failed 0
```

**Test 1 is the one that would have failed silently.** Every sandboxed pod
resolving a ClusterIP depends on `socketLB.hostNamespaceOnly=true`; without it
the rest of the cluster looks perfectly healthy while no gVisor pod can reach a
service.

### The floor holds against a hostile tenant

The design's central claim, tested directly. tenant-a — who is a full
administrator of their own cluster — authored:

```yaml
kind: NetworkPolicy
metadata: {name: tenant-tries-to-open-everything}
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
  ingress: [{}]
  egress:  [{}]
```

It **reached the host**, confirming Layer 3 now works where it silently did
nothing before:

```console
$ kubectl -n tenant-a get netpol
NAME                                                   POD-SELECTOR
tenant-tries-to-open-everything-x-default-x-tenant-a   vcluster.loft.sh/managed-by=tenant-a,...
```

And changed nothing. Re-running the deny tests with it active:

```
  PASS tenant-a client -> tenant-b server (blocked for 45s, 9 attempts)
  PASS tenant-b client -> tenant-a server (blocked for 45s, 9 attempts)
  PASS tenant-a -> internet by IP (blocked for 45s, 9 attempts)
  PASS tenant-a workload -> host API server (blocked for 45s, 22 attempts)
```

A tenant can now genuinely segment their own application, and cannot use that
same power to reach anything they were not given.

### GPU stack unaffected

Networking is orthogonal to nvproxy, and the numbers say so. Memory quota,
through the vCluster sync, under gVisor, byte-identical to the pre-migration
run:

```
meminfo: free=350 MiB total=512 MiB
alloc 0..4: 64 MiB each
alloc 5 of 64 MiB: FAILED rc=2 (CUDA_ERROR_OUT_OF_MEMORY)
meminfo: free=30 MiB (consumed 320 MiB)
```

Two tenants sharing one card for 300s:

| | before Cilium | after Cilium |
|---|---|---|
| tenant-a | 315.9 launches/s | 316.21 launches/s |
| tenant-b | 314.1 launches/s | 308.95 launches/s |

A 2.3% spread against 0.6% before. Both tenants still get their share; whether
the slightly wider gap is Cilium's datapath cost or ordinary run-to-run variance
is not established by a single run, and would need repeats to call either way.

## Label forgery: what a tenant can and cannot fake

Both floor policies name a label, and a tenant is an administrator of their own
cluster. So the whole design rests on a question that had to be answered by
experiment rather than assumption: **which of these labels can a tenant forge?**

Probes are in `manifests/cilium/forge-probe.yaml`.

### vCluster passes tenant pod labels through verbatim

The starting point, and it is worse than expected:

```console
# what the tenant set
netprobe-server   app=netprobe-server
# what landed on the host
netprobe-server-x-default-x-tenant-a   app=netprobe-server,vcluster.loft.sh/managed-by=tenant-a,...
```

No prefixing, no namespacing. **`app=vcluster` is therefore forgeable**, and
Cilium's identity for a forged pod is indistinguishable from the real control
plane's on that label:

```
control plane    k8s:app=vcluster   serviceaccount=vc-tenant-a
forged workload  k8s:app=vcluster   serviceaccount=vc-workload-tenant-a
```

The original Layer 1 carve-out — `app NotIn [vcluster]` — was consequently
worthless as a security boundary. **This was a real hole in the first design**,
and it is why the carve-out now keys on the service account.

### `vcluster.loft.sh/managed-by` cannot be forged

Tried at creation and again by `kubectl label --overwrite` after the fact. Both
times the syncer overwrote it with the true owner and relocated the tenant's
attempted value into a per-vCluster hashed key that no policy references:

```console
$ # tenant's view
forge-app   app=vcluster,vcluster.loft.sh/managed-by=escaped
$ # host's view
forge-app-x-default-x-tenant-a   app=vcluster,
    vcluster.loft.sh/label-tenant-a-x-e5f1b28ab2=escaped,
    vcluster.loft.sh/managed-by=tenant-a,...
```

Confirmed in Cilium's own identity, so the selector really does match:

```console
$ cilium-dbg identity get 31675
31675   k8s:app=vcluster
        k8s:io.cilium.k8s.namespace.labels.tenant=tenant-a
        k8s:io.cilium.k8s.policy.serviceaccount=vc-workload-tenant-a
        k8s:vcluster.loft.sh/label-tenant-a-x-e5f1b28ab2=escaped
        k8s:vcluster.loft.sh/managed-by=tenant-a
```

### The service account cannot be forged either

The sharper test, since Layer 1 now depends on it. A tenant created a service
account named exactly like the control plane's and ran a pod as it:

```console
$ # tenant asked for
spec.serviceAccountName: vc-tenant-a
$ # host runs it as
spec.serviceAccountName: vc-workload-tenant-a
```

Tenant service accounts are not synced to the host, so every workload a tenant
creates lands on the single host account `vc-workload-<tenant>` regardless of
what it asked for. Only the control plane is `vc-<tenant>`.

### Enforcement follows

Four attack pods — claiming `app=vcluster`, overwriting `managed-by`,
impersonating `tenant-b`, and forging the service account — probed against
cross-tenant, internet, and the host API server. All twelve combinations
blocked, before and after the hardening. Both tenant control planes stayed
healthy throughout, which is the thing that would have broken had the carve-out
been made too narrow.

**Conclusion:** two independent un-forgeable discriminators now carry the floor
(`managed-by`, stamped by the syncer; the service account, rewritten by it), and
the one forgeable label is out of the security path entirely. The pair is
genuinely defence in depth rather than one mechanism written twice.

## A test that lied, and the fix

Re-running the suite after hardening produced two FAILs on intra-tenant
reachability. Manual probing showed intra-tenant traffic was working perfectly.
The client pods were restarting — `sleep 86400` exiting with code 0 after a few
seconds — and `kubectl exec` against a restarting pod fails identically to a
refused connection when you only read kubectl's exit status.

That is the same false-signal class that has now bitten this project three
times, and on a *deny* test it fails silently in the dangerous direction: a
probe that never ran scores as "blocked". Two fixes, both in place:

- the probe pod runs `while true; do sleep 30; done`, so an early exit cannot
  take it down;
- the verdict is decided inside the pod and echoed back as a sentinel
  (`P_OK`/`P_NO`). No sentinel means the probe did not run, and the caller
  retries instead of concluding. A deny test where *no* probe ever ran is now
  reported INCONCLUSIVE rather than passing.

Not a gVisor defect: `sleep 60` in a gVisor pod was measured taking exactly 60s.
The root cause of the early exit is still unexplained; the harness no longer
depends on it either way.

## What broke on the way, and why it is worth knowing

The migration failed the first time in a way that pointed at entirely the wrong
thing, and the fix is now baked into `migrate-to-cilium.sh`.

k3s does not use the CNI defaults. Its containerd is configured with
`conf_dir=/var/lib/rancher/k3s/agent/etc/cni/net.d` and
`bin_dirs=[/var/lib/rancher/k3s/data/cni]`, while Cilium installs to
`/etc/cni/net.d` and `/opt/cni/bin`. Left at the defaults, Cilium came up
entirely healthy — agent OK, operator OK, kube-proxy replacement active — while
the kubelet reported:

```
NetworkReady=false reason:NetworkPluginNotReady
message:Network plugin returns error: cni plugin not initialized
```

The node went `NotReady`, took a `node.kubernetes.io/not-ready:NoSchedule`
taint, and every pod — including Cilium's own Hubble Relay — sat `Pending` with
"untolerated taint". Every visible symptom pointed at scheduling. The cause was
a path mismatch two layers down. Setting `cni.confPath` and `cni.binPath` fixed
it in one Helm upgrade.

## What this does not close

- **The forgery result is version-specific.** That `managed-by` and the service
  account are rewritten is behaviour of vCluster 0.36.1, not a documented
  guarantee. A vCluster upgrade should re-run `forge-probe.yaml` before being
  trusted — the whole floor rests on it.
- **Egress is exception-listed, not identity-aware.** `toFQDNs` is where this
  should go next; it is the reason Cilium was chosen over Calico. Not in scope
  for the first cut.
- **NodePort collisions between tenants** remain unmanaged; tenant NodePorts are
  hand-assigned (30443, 31443) with no admission control preventing overlap.
- **No encryption.** Irrelevant on one node; mandatory the moment this is more
  than one node, and the reason WireGuard support was a selection criterion.
- **Hubble is enabled but unused.** Per-tenant flow audit is a natural follow-on
  and is most of why observability featured in the CNI choice.

## Applying it

Done, via `migrate-to-cilium.sh` (which now carries the CNI-path fix above).
`/etc/rancher/k3s/config.yaml` holds:

```yaml
flannel-backend: none
disable-network-policy: true
disable-kube-proxy: true
egress-selector-mode: cluster
```

To re-run the isolation tests at any time:

```bash
bash test-isolation.sh
```

The four `netprobe` pods are deliberately left running in the two tenants so
this can be re-run without setup. They are two busybox pods per tenant and cost
almost nothing; delete them with
`kubectl delete pod netprobe-client netprobe-server` against each tenant's
kubeconfig if you want the namespaces clean.
